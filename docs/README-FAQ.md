# 常见问题

中文 | [English](./README-FAQ_EN.md)

## 采集与数据

### 搭建完成后为什么看不到影片？

发行镜像不包含影视数据。首次启动会写入默认采集源，但不会自动跑完采集。须在管理后台执行采集；首次全量可能持续数小时，源站越多耗时越长。

前台、后台影片列表以及 TVBox / MacCMS 都读取快照 / 内存读模型，而不是采集过程中的业务表。入库成功的页会按窗口刷进快照，主站影片边采边出现在前台；尚未刷出任何快照时表现为空站，属预期行为。

### 主站是什么？

主站是已启用采集站里排序最前的一座。前台首页、分类、搜索、每日更新只看这一站自己已经采过的片子和分类。换成另一座启用站，前台立刻换成那一站已有的数据。不重采，也不删其他站的档案。

播放页从主站这部片子出发，按匹配键补上其他已启用站已经采到的线路。线路按站分开。海报源是单独的标记，不决定主站。前台封面用海报源对上的那部影片当前的封面。对不上才用主站自己的图。海报源就是主站时，用主站自己的图。没有启用站时，按同一顺序取第一名兜底。

### 切换主站会清掉什么？

不删片，不重采。会清空线上轮播和排片规则。采集进行中也可以切换。

更换某一站的采集地址，会清空这一站的档案、线路、失败记录和分类，有没有播放线路都清，并重新拉取分类。其他站不动。这和切换主站是两件事。删除一个站同样只清这一站。

### 影片如何去重、如何跨站对齐？

各站各留一份档案，采集时不合并。

- 站内：`movie_source_mapping` 用采集站和源站 `vod_id` 认出自己的旧档案，再次采集只更新这一条。同一站、同一页里匹配键相同的条目合成一部。
- 跨站：匹配键不拿来合并档案。播放页读取时用它找其他已启用站的同一部，把那些站自己的线路附在后面。顺序是豆瓣 ID + 片名，然后片名#大类，再纯片名。多个键命中同一部只出一次。线路按站分开，不跨站拼集。

分类键是 `source:{本站}:{typeId}`，跟该站自己的分类树一致。

### 刮削和首页轮播存在哪？

影片刮削直接改这部片子选中的封面、简介、评分等。片名和分类不动。没有还原。首页轮播的刮削写在轮播那一行，不改片子，也没有另一张刮削表。首页用轮播行自己的图和简介，更新状态跟片库。

### 手动停止采集后数据处于什么状态？

停止会中断仍在拉页的任务，并取消对应 context。已经成功入库的页留在 `film_index`；失败页进入重试队列。收尾只冲掉剩余发布缓冲。

## 快照与缓存

### 采集过程中为什么要刷快照？窗口发布为何仍可能耗时？

采集过程中库表持续变化。每窗刷新本批播放摘要，并按 mid 增量更新内存检索索引。前台列表、筛选、后台影片列表和 TVBox / MacCMS 都读 `film_index`。

列表缓存约 5 秒防抖，避免每页清 Redis。检索全量重建只在启动时分页加载。

### 修改配置后前台为什么没有立刻变化？

网站配置写入后会更新 Redis 并清理首页缓存。若页面仍旧，常见原因是浏览器、CDN 或反向代理缓存，或当前进程不是最新代码。

影片列表、分类、筛选只看当前主站自己的档案。切换主站后立刻展示新主站已经入库的片子；这一站还没采过则为空。TVBox 常规列表另有 Redis 缓存（最长约 12 小时），入库后会按防抖清理；若仍不一致，优先核对运行实例与请求参数。

### 「最近更新」按什么排序？分类页和 TVBox 是否一致？

最近更新按 `film_index.update_stamp` 降序（同分再按 `mid`）。新片保留源站给出的时间。已在库里的片子，播放线路内容有变化时，才把这个时间改成当前采集时间。只改下载线路、备注、演员或封面，不改这个排序。各采集站同一套规则。

前台分类筛选与 TVBox 走同一套读模型规则（分类、剧情 / 地区 / 语言 / 年份、排序）。TVBox 常规列表多一层 Redis 缓存，因此短时间不一致时先看缓存。

## 登录与权限

### 后台页面能打开，接口却提示未登录？

边缘中间件只检查 `ecohub_auth_token` cookie 是否存在。打开 `/manage` 时，服务端 layout 还会请求 `/api/manage/user/info`，由后端校验 JWT 与 Redis token；失败会跳转 `/login`。已经打开的后台页在 token 事后失效（过期、被其它设备顶掉、Redis 中已失效）时，后续接口仍可能返回未登录。以后端返回为准。

### 访客账号与默认账号如何使用？

初始化只创建超级管理员 `admin` / `admin`。普通用户和访客在账号管理中新建。访客可调用管理端 GET；POST / PUT / PATCH / DELETE 会被 `WriteAccess` 拒绝。对外部署后须立即修改默认密码。
