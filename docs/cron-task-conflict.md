# 计划任务运行冲突

采集与维护撞车时，采集让行，冲突只跳过。维护不等采集跑完，也不因为超时放弃自己。

## 任务

| 任务 | 类型 | 默认时刻 |
|---|---|---|
| `sys_cron_auto_collect` | 采集 | 每小时整点，窗口 24 小时 |
| `sys_cron_orphan_clean` | 维护 | 每天 02:00 |
| `sys_cron_log_clean` | 维护 | 每天 03:00 |
| `sys_cron_collect_clean` | 维护 | 每天 03:30 |

类型 0 是采集。片库清理、日志清理、采集记录清理都是维护。

## 规则

1. 同一时刻只跑一条维护。后到的维护本轮跳过，不等、不排队、不打断正在跑的那条。
2. 同一秒到点的多条维护按入队顺序逐条做完。前一条结束再开始下一条。某一条失败只通知这一条，后面的照常跑。
3. 维护与采集撞上时，这一轮采集跳过。定时触发、手动立即执行、采集中心开批次都一样。
4. 采集已经在跑时，维护先占住闸门，立刻停止采集，只等已经在写的事务、这次运行和这批收尾发布退出，然后马上清理。
5. 跳过只打日志。不记采集失败，不进熔断，不发采集失败通知，不改上次运行时间。
6. 写事务或已停止的运行在退出上限内收不掉，这次维护失败并通知，不开始清理。

退出上限沿用删除站点时等待本次运行退出的时间（3 分钟）。这只覆盖停止之后尚未退出的写事务和运行，不是等采集把剩余页数跑完。

上次运行时间只在维护真正开始清理、或定时采集真正开工时写入。调度入队、让行、跳过都不算。

被跳过的定时采集不补跑。下次定时采集按各站上次成功时间补窗，最多 7 天。已入库的数据保留。

## 时间线

同一秒：02:00 的片库清理和整点采集一起到点。采集整批跳过，片库清理开工。

采集已开始：11:59 的采集还在跑，00:00 维护到点。维护占住闸门，停止这批采集。还没开工的站点标成已停止。正在写的事务写完后开始清理。清理结束后采集不续跑，下一整点补窗。

维护重叠：02:00 的片库清理到 03:00 还在跑。03:00 的日志清理和整点采集都跳过。日志清理留到下一次 03:00。

同一秒的两条维护：先做先入队的那条，做完再做下一条。这一秒的采集跳过。

手动执行：维护进行中再执行采集，直接返回「维护中，已跳过」。再执行另一条维护，直接返回「已有维护任务在执行」。

## 实现

- `spider_cron_dispatch.go`：1 秒合并后裁决。已有维护在跑时，本批采集和维护全部跳过。没有维护在跑时，同批维护顺序执行，采集跳过。
- `spider_cron.go`：三条维护共用开工流程。删掉 10 分钟等待和超时跳过。
- `collect_lifecycle.go`：闸门只表示维护占用。占用失败立即返回。维护先停采集，再等在途写入和运行退出，然后独占清理。
- 采集入口：维护中不开新批次。已经走到单站开工的，按已停止跳过，不写失败。

停采集走 `StopAllCollect(reason)`。日志写明原因：维护让行、用户一键终止、用户停止该站、采集站已停用、删除采集站、导入配置、清空片库、进程退出。后续派发和单站跳过沿用同一次原因，不再笼统写成一键终止。
