# 计划任务运行冲突

一句话规则：**同一时段有维护任务，优先跑维护，非维护任务跳过；同一时段多个维护任务，排队依次执行。**

## 任务

| 任务 | 类型 | 默认时刻 |
|---|---|---|
| `sys_cron_auto_collect` | 采集 | 每小时整点，窗口 24 小时 |
| `sys_cron_orphan_clean` | 维护 | 每天 02:00 |
| `sys_cron_log_clean` | 维护 | 每天 03:00 |
| `sys_cron_collect_clean` | 维护 | 每天 03:30 |

类型 0 是采集。片库清理、日志清理、采集记录清理都是维护。

## 规则

1. 维护优先。同一时段（1 秒合并窗口）到点的任务里只要有维护，本批采集全部跳过；已有维护在执行或在排队时，到点的采集也跳过。跳过的采集不排队、不补跑。
2. 维护排队。所有维护进同一个先进先出队列，由一个工作协程依次执行，前一条结束再开始下一条，不跳过、不丢弃。同一任务已在排队或正在执行时不重复入队。
3. 开跑前读取最新配置。定时触发的维护在轮到自己时已被停用，则跳过这一条，继续下一条。
4. 每条维护执行时都占用维护闸门：先停止在途采集，只等已经在写的事务、这次运行和这批收尾发布退出，然后独占清理。闸门被其他短暂的独占操作（如采集站接口探测）占用时等待，最多 10 分钟，超时告警。
5. 某一条维护失败或 panic，只对这一条发送定时任务失败告警，队列里后面的照常执行。
6. 采集被跳过只打日志。不记采集失败，不进熔断，不发采集失败通知，不改上次运行时间。
7. 写事务或已停止的运行在退出上限内收不掉，这次维护失败并通知，不开始清理。

退出上限沿用删除站点时等待本次运行退出的时间（3 分钟）。这只覆盖停止之后尚未退出的写事务和运行，不是等采集把剩余页数跑完。

上次运行时间只在维护真正开始清理、或定时采集真正开工时写入。调度入队、排队、跳过都不算。

被跳过的定时采集不补跑。下次定时采集按各站上次成功时间补窗，最多 7 天。已入库的数据保留。

## 时间线

同一秒：02:00 的片库清理和整点采集一起到点。采集跳过，片库清理开工。

同一秒多条维护：两条维护同时到点，按到点顺序入队，先做第一条，做完再做第二条。这一秒的采集跳过。

维护重叠：02:00 的片库清理到 03:00 还在跑。03:00 的整点采集跳过；03:00 的日志清理进队列排队，片库清理结束后立刻执行；03:30 的采集记录清理排在日志清理后面。04:00 时若队列仍未清空，04:00 的整点采集也跳过。

采集已开始：11:59 的采集还在跑，00:00 维护到点。维护占住闸门，停止这批采集。还没开工的站点标成已停止。正在写的事务写完后开始清理。清理结束后采集不续跑，下一整点补窗。

手动执行：
- 维护执行或排队中再手动执行采集，直接返回「维护中，已跳过」。
- 维护执行中再手动执行另一条维护，加入队列，返回「已有维护任务在执行，本任务已排队，前一条结束后自动执行」；没有维护在跑时直接开始。手动执行不受任务启用开关限制。
- 同一维护已在排队或执行中，再次手动执行会提示已在排队或执行中。
- 任务列表里排队中的任务显示「排队中」。

## 实现

- `spider_cron_dispatch.go`：1 秒合并后裁决。本批有维护或已有维护在执行/排队时，采集全部跳过；本批维护按到点顺序入队。
- `maintenance_queue.go`：维护串行队列。单工作协程、按任务去重、开跑前读最新配置、panic 兜底后继续下一条。
- `spider_cron.go`：三条维护共用开工流程（`executeMaintenance`）；手动执行 `RunTaskOnceWithStatus`。
- `collect_lifecycle.go`：闸门表示维护占用。维护先停采集，再等在途写入和运行退出，然后独占清理。
- 采集入口：维护中（含排队）不开新批次。已经走到单站开工的，按已停止跳过，不写失败。

停采集走 `StopAllCollect(reason)`。日志写明原因：维护让行、用户一键终止、用户停止该站、采集站已停用、删除采集站、导入配置、清空片库、进程退出。后续派发和单站跳过沿用同一次原因，不再笼统写成一键终止。
