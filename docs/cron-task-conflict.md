# 计划任务运行冲突

中文 | [English](./cron-task-conflict_EN.md)

## 一句话规则

**同一时段有维护任务，优先跑维护，采集任务跳过；同一时段有多个维护任务，排队依次执行。**

## 任务

后台「计划任务」里默认有 4 条任务，默认时间都是北京时间（镜像时区 `Asia/Shanghai`）：

| 任务 ID | 名称 | 类型 | 默认时间 |
| --- | --- | --- | --- |
| `sys_cron_auto_collect` | 采集已启用站点的更新 | 采集 | 每小时整点，采最近 24 小时 |
| `sys_cron_orphan_clean` | 清理片库冗余和孤儿数据 | 维护 | 每天 02:00 |
| `sys_cron_log_clean` | 清理过期运行日志 | 维护 | 每天 03:00 |
| `sys_cron_collect_clean` | 定期清理超过 30 天的采集运行记录与快照 | 维护 | 每天 03:30 |

任务类型 `0` 是采集，其余（片库清理、日志清理、采集记录清理）都是维护。

## 规则

1. **维护优先。** 1 秒内到点的任务算同一批。这一批里只要有维护，采集全部跳过；已经有维护在执行或在排队时，到点的采集也跳过。跳过的采集不排队、不补跑。
2. **维护排队。** 所有维护进同一个先进先出队列，由一个工作协程依次执行，前一条结束才开始下一条，不跳过、不丢弃。同一条维护已经在排队或正在执行时，不会重复入队。
3. **开跑前读最新配置。** 定时触发的维护轮到自己时，如果已经被停用，就跳过这一条，接着跑下一条。
4. **维护要先让采集停下。** 每条维护开跑时占住「维护闸门」：先停掉正在跑的采集，等已经在写的事务、这次采集运行和收尾发布退出，再独占清理。闸门被其他短暂的独占操作（如采集站接口探测）占着时，最多等 10 分钟，超时就告警。
5. **失败只影响自己。** 某条维护失败或 panic，只为这一条发送「定时任务失败告警」，队列里后面的照常执行。
6. **采集被跳过只打日志。** 不记采集失败，不进熔断，不发采集失败通知，不改上次运行时间。
7. **停不下来就不清理。** 停采集后，写事务或已停止的运行在退出上限内没有退出，这次维护失败并通知，不开始清理。

退出上限沿用删除采集站时等待采集退出的时间，3 分钟。它只等停止之后还没退出的写事务和运行，不是等采集把剩下的页跑完。

上次运行时间只在维护真正开始清理、或定时采集真正开工时写入。入队、排队、跳过都不算。

被跳过的定时采集不补跑。下一次定时采集会按每个采集站上次成功的时间补齐中间的窗口，最多补 7 天。已经入库的数据不受影响。

维护队列只在内存里。服务重启后，还在排队的维护会丢失，等下一次到点再跑。

## 例子

**采集和维护同一秒到点。** 02:00 片库清理和整点采集一起到点。采集跳过，片库清理开始。

**多条维护同一秒到点。** 两条维护按到点顺序入队，先跑第一条，跑完再跑第二条。这一秒的采集跳过。

**维护跑得久，和后面的任务重叠。** 02:00 的片库清理到 03:00 还没跑完：

- 03:00 的整点采集跳过。
- 03:00 的日志清理进队列，片库清理一结束就执行。
- 03:30 的采集记录清理排在日志清理后面。
- 04:00 时队列如果还没清空，04:00 的整点采集也跳过。

**采集已经在跑，维护到点。** 01:00 的整点采集到 02:00 还在跑，02:00 片库清理到点（同一秒的 02:00 整点采集跳过）：

1. 片库清理占住闸门，停掉 01:00 那批采集，还没开工的采集站标成已停止。
2. 正在写的事务写完后，开始清理。
3. 清理结束后，01:00 那批采集不会接着跑。03:00 的整点采集也会被日志清理挡掉；等维护全部跑完，下一次整点采集按上次成功时间补窗。

**手动执行。**

- 维护在执行或排队时，手动执行采集：直接返回「维护中，已跳过」。
- 维护在执行时，手动执行另一条维护：加入队列，返回「已有维护任务在执行，本任务已排队，前一条结束后自动执行」。没有维护在跑时直接开始。
- 手动执行维护不受任务启用开关限制，停用的维护也能手动跑。
- 同一条维护已经在排队或执行中，再手动执行会提示已在排队或执行中。
- 任务列表里，排队中的任务显示「排队中」。

## 实现

代码都在 `server/internal/spider/`：

| 文件 | 负责什么 |
| --- | --- |
| `spider_cron_dispatch.go` | 1 秒合并同一批到点任务后裁决：这批有维护、或已有维护在执行或排队时，采集全部跳过；维护按到点顺序入队 |
| `maintenance_queue.go` | 维护串行队列：单个工作协程、按任务去重、开跑前读最新配置、panic 兜底后继续下一条 |
| `spider_cron.go` | 三条维护共用的开工流程 `executeMaintenance`；手动执行入口 `RunTaskOnceWithStatus` |
| `collect_lifecycle.go` | 维护闸门：维护先停采集，再等在途写入和运行退出，然后独占清理 |
| `collect_control.go` | 停止采集 `StopAllCollect`、`StopCollectSource`，以及 3 分钟退出上限 `deleteStopTimeout` |

采集入口：维护中（包括排队中）不开新批次。已经走到单站开工的，按「已停止」跳过，不记失败。

停采集走 `StopAllCollect(reason)`（停全部）或 `StopCollectSource(id, reason)`（停一站），日志里写明原因，例如：维护让行、用户一键终止、用户停止该站、采集站已停用、导入采集站配置、清空片库、进程退出。后续派发和单站跳过沿用同一个原因，不再笼统写成一键终止。
