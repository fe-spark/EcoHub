# 计划任务运行冲突

中文 | [English](./cron-task-conflict_EN.md)

## 规则摘要

**同一时段存在维护任务时，优先执行维护任务，采集任务跳过；同一时段存在多个维护任务时，按顺序排队执行。**

## 相关对象

后台「计划任务」默认包含 4 条任务，默认时间均为北京时间（镜像时区 `Asia/Shanghai`）：

| 任务 ID | 名称 | 类型 | 默认时间 |
| --- | --- | --- | --- |
| `sys_cron_auto_collect` | 采集已启用站点的更新 | 采集 | 每小时整点，采集最近 24 小时 |
| `sys_cron_orphan_clean` | 清理片库冗余和孤儿数据 | 维护 | 每天 02:00 |
| `sys_cron_log_clean` | 清理过期运行日志 | 维护 | 每天 03:00 |
| `sys_cron_collect_clean` | 定期清理超过 30 天的采集运行记录与快照 | 维护 | 每天 03:30 |

任务类型 `0` 为采集，其余类型（片库清理、日志清理、采集记录清理）均为维护。

## 规则

1. **维护优先。** 1 秒内触发的任务视为同一批。同一批中只要包含维护任务，所有采集任务均跳过；已有维护任务正在执行或排队时，触发的采集任务同样跳过。跳过的采集任务不排队，也不补执行。
2. **维护排队。** 所有维护任务进入同一个先进先出队列，由单个工作协程依次执行，前一条结束后才开始下一条，不跳过、不丢弃。同一条维护任务已在排队或执行中时，不会重复入队。
3. **执行前读取最新配置。** 定时触发的维护任务轮到执行时，如已被停用，则跳过该任务并继续执行下一条。
4. **维护前先停止采集。** 每条维护任务开始时占用「维护闸门」：先停止正在运行的采集，等待已开始的写事务、本次采集运行和收尾发布退出，再独占执行清理。闸门被其他短暂的独占操作（如采集站接口探测）占用时，最多等待 10 分钟，超时则告警。
5. **失败互不影响。** 某条维护任务失败或 panic 时，仅针对该任务发送「定时任务失败告警」，队列中的后续任务照常执行。
6. **跳过采集仅记录日志。** 不记为采集失败，不计入熔断，不发送采集失败通知，不更新上次运行时间。
7. **无法停止采集时不执行清理。** 停止采集后，如写事务或已停止的运行未在退出上限内退出，本次维护任务失败并发送通知，不开始清理。

退出上限沿用删除采集站时等待采集退出的时间，即 3 分钟。该上限只用于等待停止后尚未退出的写事务和运行，不等待采集完成剩余页面。

上次运行时间仅在维护任务实际开始清理、或定时采集实际开始执行时写入。入队、排队和跳过均不更新该时间。

被跳过的定时采集不补执行。下一次定时采集会按各采集站上次成功的时间补齐中间的时间窗口，最多补 7 天。已入库的数据不受影响。

维护队列仅保存在内存中。服务重启后，排队中的维护任务会丢失，在下一次触发时间执行。

## 示例

**采集任务与维护任务在同一秒触发。** 02:00 片库清理与整点采集同时触发：采集跳过，片库清理开始执行。

**多条维护任务在同一秒触发。** 两条维护任务按触发顺序入队，第一条执行完成后执行第二条。同一秒的采集任务跳过。

**维护任务耗时较长，与后续任务重叠。** 02:00 的片库清理到 03:00 仍未完成：

- 03:00 的整点采集跳过。
- 03:00 的日志清理进入队列，片库清理结束后立即执行。
- 03:30 的采集记录清理排在日志清理之后。
- 04:00 时如队列仍未清空，04:00 的整点采集同样跳过。

**采集正在运行时维护任务触发。** 01:00 的整点采集到 02:00 仍在运行，02:00 片库清理触发（同一秒的 02:00 整点采集跳过）：

1. 片库清理占用闸门，停止 01:00 的采集批次，尚未开始的采集站标记为已停止。
2. 正在执行的写事务完成后，开始清理。
3. 清理结束后，01:00 的采集批次不会继续执行。03:00 的整点采集也会因日志清理而跳过；所有维护任务完成后，下一次整点采集按上次成功时间补齐时间窗口。

**手动执行。**

- 维护任务正在执行或排队时，手动执行采集：直接返回「维护中，已跳过」。
- 维护任务正在执行时，手动执行另一条维护任务：加入队列，返回「已有维护任务在执行，本任务已排队，前一条结束后自动执行」。没有维护任务运行时直接开始执行。
- 手动执行维护任务不受任务启用开关限制，已停用的维护任务也可以手动执行。
- 同一条维护任务已在排队或执行中时，再次手动执行会提示已在排队或执行中。
- 任务列表中，排队中的任务显示为「排队中」。

## 实现

相关代码位于 `server/internal/spider/`：

| 文件 | 职责 |
| --- | --- |
| `spider_cron_dispatch.go` | 将 1 秒内触发的任务合并为一批后进行裁决：该批包含维护任务、或已有维护任务正在执行或排队时，跳过全部采集任务；维护任务按触发顺序入队 |
| `maintenance_queue.go` | 维护任务串行队列：单个工作协程、按任务去重、执行前读取最新配置、panic 恢复后继续执行下一条 |
| `spider_cron.go` | 三条维护任务共用的执行流程 `executeMaintenance`；手动执行入口 `RunTaskOnceWithStatus` |
| `collect_lifecycle.go` | 维护闸门：维护任务先停止采集，等待在途写入和运行退出，再独占执行清理 |
| `collect_control.go` | 停止采集 `StopAllCollect`、`StopCollectSource`，以及 3 分钟退出上限 `deleteStopTimeout` |

采集入口：维护期间（包括排队期间）不启动新批次。已进入单站执行阶段的采集按「已停止」跳过，不记为失败。

停止采集通过 `StopAllCollect(reason)`（停止全部）或 `StopCollectSource(id, reason)`（停止单站）完成，日志中记录停止原因，例如：维护让行、用户一键终止、用户停止该站、采集站已停用、导入采集站配置、清空片库、进程退出。后续派发和单站跳过沿用同一原因，不统一记为一键终止。
